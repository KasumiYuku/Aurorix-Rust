# 架构

一条消息从收到到发出：接入 → 路由 → 渲染 → 发送 → 入库。
插件只在「路由」这一步出现，接入、页脚、出图、发送、入库都由框架完成。
这一页只讲东西放在哪、消息怎么走，细节留给各自的文档。

## 模块地图

| 目录 | 干什么 |
|---|---|
| `crates/aurorix-gateway` | 接入：与平台保持长连接、心跳重连、收 Webhook |
| `crates/aurorix-api` | 平台调用：发消息、传文件、撤回、频控 |
| `crates/aurorix-plugin` | 指令与任务：指令树、参数、权限、冷却、定时任务 |
| `crates/aurorix-render` | 出图：排队、绘制、编码 |
| `crates/aurorix-assets` | 图床：多家 Provider 的优先级与降级 |
| `crates/aurorix-db` | PostgreSQL：KV、统计、收件箱、插件自己的表 |
| `crates/aurorix-admin` | 管理台：HTTP 接口与内嵌页面 |
| `crates/aurorix-bot` | 装配运行时：把上面这些接起来并跑事件循环 |

## 一条消息的经历

1. 接入：网关收到平台事件，转成框架内部统一的一条消息。
2. 去重：同一 `event_id` 或 `message_id` 在 300 秒内只处理一次。
3. 维护：全局维护开着就直接回维护文案，不进指令路由。
4. 路由：按前缀和别名找到指令，依次检查权限、名单、参数、冷却。
5. 执行：调用插件处理器，它可以读 KV、查自己的表、要一张图。
6. 出站：回复先合并页脚按钮，需要出图的交给渲染。
7. 发送：文本、Markdown、图片交给平台 API，失败按类型记录。
8. 入库：收发计数和消息正文写进统计表与收件箱。

## 出图为什么不会拖慢机器人

- 渲染跑在独立线程池，异步侧只等结果，不占 I/O 线程。
- 有可用 GPU 就用 GPU，不能用就整体回退多线程 CPU 光栅，只回退一次。
- 渲染队列满了直接报错，不无限排队；出图失败改发纯文本，业务不中断。

## 四种会话

| 场景 | 标识 | 文本形态 | 图片形态 |
|---|---|---|---|
| 群聊 | `group` | Markdown | 上传后按图片消息发 |
| 私聊 | `c2c` | Markdown | 上传后按图片消息发 |
| 频道 | `channel` | 纯文本 | 分片上传后带 `msg_id` 发 |
| 频道私信 | `dm` | 纯文本 | 同频道 |

频道里 Markdown 不会渲染，所以需要样式的内容一律出图。

## 出问题时先看这里

| 现象 | 先看哪 |
|---|---|
| 消息没反应 | 网关是否连上、前缀是否对、`/help` 里有没有这条指令 |
| 图片发不出 | 渲染是否超时、图床是否全部失败进了冷却 |
| 数据没写进去 | 数据库连接是否健康、批处理是否刷盘 |

## 停机

- 先停网关，不再接新事件，再广播关闭信号。
- 等在飞任务跑完，超出预算的任务被中止并记一次超时。
- 最后关数据库连接池、释放单实例锁，输出一份停机报告。
